# Instructions for Adding a CrocoLake Converter

Use this guide when adding support for a new observational dataset. Follow the
existing GLODAP, SprayGliders, Saildrones, and SPOTS implementations rather
than creating a separate workflow.

## Start in plan mode

Always begin the task in plan mode. First inspect the repository, the source
data, and the supplied documentation, then present a structured implementation
plan for developer approval before making code changes.

If any requirement, dataset semantic, QC rule, profile definition, output
behavior, or scope boundary is uncertain, ask the developer a clarifying
question. Do not silently choose an interpretation or make assumptions when
multiple reasonable options exist.

## 1. Inspect the source and documentation first

Before editing code:

1. Inspect the complete source-file inventory and representative rows.
2. Read the dataset documentation, especially definitions for:
   - platform or site identifiers;
   - cruise, deployment, station, cast, cycle, and bottle identifiers;
   - date/time fields;
   - measurement units;
   - quality-control flags and missing-value conventions.
3. Determine which variables belong in PHY and which belong in BGC.
4. Identify the fields that uniquely define one profile:
   a profile is a collection of measurements at multiple depths for one
   platform/location/time or source-defined cast.

Do not assume that a source `CASTNO` or profile number is globally unique.
Check whether it resets by platform, cruise, or station. Bottle/sample
identifiers normally identify observations within a profile and must not be
used as the profile identifier.

## 2. Extend the parameter registry

Update `crocolaketools/db_params.py` with:

- `params["<DB>"]`: the original source fields worth retaining or documenting;
- `params["<DB>2CROCOLAKE"]`: the source-to-standardized rename map;
- any temporary source names generated by the converter, such as
  `profile_nb` and `date_update`;
- `params["CROCOLAKE2<DB>"]` if reverse lookups or integrity tests need them.

Use the standardized CrocoLake names already present in
`CROCOLAKE_PHY_QC` and `CROCOLAKE_BGC_QC`. Do not add source metadata to the
output mapping unless it belongs in the CrocoLake schema.

Update `crocolaketools/db_names.py` with the canonical database name.

## 3. Implement the converter

Create `crocolaketools/converter/converter<DB>.py` inheriting from
`Converter`.

Match the style of existing converters:

- Doxygen-style file header;
- separator banners before methods;
- `Arguments` and `Returns` docstrings;
- existing naming, spacing, and logging conventions.

Implement the source-specific methods needed for:

- reading one or more source files;
- normalizing source dates/times into `JULD`;
- applying source QC flags;
- creating error columns from precision/accuracy fields;
- generating profile identifiers;
- calling `super().standardize_data()` after source-specific preparation.

### Profile identifiers

`CYCLE_NUMBER` must be a progressive integer starting at `1` for each
`PLATFORM_NUMBER`, following the behavior of `ConverterGLODAP`.

If the source does not provide a suitable identifier:

1. Build a composite profile key from documented metadata.
2. Deduplicate the profile keys.
3. Sort them deterministically.
4. Use `groupby("PLATFORM_NUMBER").cumcount() + 1`.
5. Map the assigned numbers back to all observations.

Do not use raw hash values as `CYCLE_NUMBER`. Hashes may be used internally as
temporary join keys, but the stored identifier must be a small progressive
integer. Decide whether IDs are assigned before or after QC filtering based on
the source precedent and developer requirements. GLODAP assigns IDs before
QC filtering, so an entirely removed profile can leave a gap in the output;
SPOTS follows changes the ordering for gap-free output. If gap-free output numbering is required,
ask the developer before changing this ordering.

## 4. Respect Dask dataframe behavior

Source converters generally read data with Dask. Operations that use pandas
row-wise behavior, `.loc`, `groupby`, or custom functions must run through
`map_partitions()` with suitable metadata where Dask cannot infer the result.

Examples:

```python
ddf = ddf.map_partitions(add_datetime)
ddf = ddf.map_partitions(keep_best_values, flag_column)
ddf = ddf.map_partitions(add_error_column, value_name)
```

Use `compute()` only for genuinely global metadata operations, such as
building a small unique profile-key lookup. Avoid unnecessary `persist()`
calls.

Shuffle messages from `drop_duplicates()`, sorting, grouping, and repartitioning
are expected. They are not errors unless followed by failed tasks or an
exception.

## 4.1 Shared base-converter contracts

The base `Converter` performs important common work after source-specific
reading:

1. optionally adds derived TEOS-10 variables;
2. applies `cols_to_convert` unit conversions;
3. reorders required identifier columns;
4. removes duplicate rows;
5. sorts by `PLATFORM_NUMBER`, `CYCLE_NUMBER`, and `PRES`;
6. repartitions and writes Parquet using the generated schema.

Source converters should return a Dask dataframe with the required standardized
columns before relying on this pipeline. `standardize_data()` renames source
columns, drops variables outside the selected PHY/BGC schema, adds missing
optional variables/QC/error columns, adds `DB_NAME`, wraps longitude to
`[-180, 180)`, and generates the storage schema.

Derived variables require valid `PRES`, `TEMP`, `PSAL`, latitude, and longitude.
Do not enable `add_derived_vars` until the source pressure, temperature, and
salinity fields and units have been verified.

If a converter builds a Dask dataframe from delayed pandas results, set
`call_guess_schema = True` when the normal reference schema cannot describe
the delayed result. Otherwise, use the normal reference schema path.

## 4.2 Patterns from existing non-Argo converters

Use the closest pattern, but do not copy an implementation without checking its
assumptions:

- **GLODAP:** single CSV, source QC flags ending in `f`, custom profile
  numbering, and complex global Dask operations for progressive IDs. Good
  precedent for casts and per-platform/profile-number semantics.
- **SprayGliders:** large NetCDF files require a separate `prepare_data()` step
  that chunks only the profile dimension into temporary NetCDF files. Use a
  Dask `Lock` for shared NetCDF access, restart the client between preparation
  and conversion when necessary, and clean up temporary files afterward.
  `call_guess_schema` is enabled because data is built from delayed pandas
  results.
- **Saildrones:** delayed NetCDF reads may need explicit row chunking for
  memory control. Multiple sensor columns can map to one CrocoLake variable
  and must be merged deliberately. Sensor depths are defined by
  `Saildrones_depth_map`, observations are reshaped to long depth records, and
  `DOXY` uses a configured unit conversion. Its cycle number is derived from
  mission start year and is not a generic cast counter; verify whether that
  source-specific convention is appropriate before reusing it.
- **OleanderXBT:** delayed NetCDF processing is simpler, but still requires
  locks, explicit resource cleanup, pressure calculation from depth, and
  removal of rows without temperature. Its source trajectory/profile fields
  provide the platform/cycle identity.
- **SPOTS:** single CSV with both PHY and BGC variables, source WOCE flags,
  precision/accuracy error fields, and profile keys composed from site, cruise,
  station, and cast. Bottle numbers identify samples within a cast and are not
  profile keys.

Common source-specific patterns include converting depth to pressure with GSW,
adding QC flags when the source has no explicit QC column but the measurement
is trusted, and removing rows only after determining which measurements are
meaningful for the selected database type.

Every output must provide the identifiers expected by the base pipeline:
`DB_NAME`, `JULD`, `LATITUDE`, `LONGITUDE`, `PLATFORM_NUMBER`,
`CYCLE_NUMBER`, and `PRES` where the selected schema requires them. If the
source does not contain one of these, define and document a deterministic
replacement before calling the base conversion path.

## 4.3 Delayed NetCDF and locking checklist

For NetCDF converters using `dask.delayed`:

- open datasets inside the delayed function;
- use the repository's lock pattern around shared NetCDF operations;
- release locks in `finally` blocks;
- close xarray datasets explicitly;
- return both the pandas dataframe and the variables actually read when
  downstream processing needs source-variable metadata;
- provide Dask metadata when custom partition functions cannot infer it;
- test both one-file and multiple-file paths if the converter overrides
  `convert()`.

Do not hold a lock longer than necessary, but do not remove it merely to avoid
serialization issues without understanding the underlying NetCDF access.

## 4.4 Units, longitude, schema, and output behavior

- Define source unit conversions in `self.cols_to_convert` and verify them
  against source documentation. Do not silently reinterpret units in a
  rename map.
- Depth-to-pressure conversion is source-specific and should use GSW with the
  documented sign convention and latitude.
- The base converter expects longitude in `[-180, 180)`. If a source uses
  `[0, 360)`, explicitly choose and document whether to shift it; the default
  path raises an error rather than silently changing the range.
- The base reference schema is the CrocoLake QC schema. Variables not in the
  selected PHY/BGC schema are dropped, even if they were present in the source.
- Missing optional variables are added as typed null columns when their
  standardized names are in the source mapping. Confirm that all expected
  source variables are represented in the mapping before conversion.
- `overwrite=False` raises when the output directory already contains files;
  `overwrite=True` replaces the existing dataset. Choose this deliberately in
  configuration and tests.
- Parquet files use the configured basename plus numbered partitions, and a
  metadata file is written. Validate the dataset directory, not just one
  partition file.

Configuration and script conventions are not perfectly uniform across the
older converters. Verify that the script's database name, config key,
constructor arguments, output basename, and cluster profile all agree. In
particular, do not copy a script's user-defined configuration dictionary
without checking its `db` value and whether the current base constructor
expects a single config dictionary.

## 5. Add the conversion script

Create `scripts/<db>2parquet.py` following the style of
`glodap2parquet.py` or `spray2parquet.py`.

The script should:

- support `--config`;
- support explicit input/output arguments where appropriate;
- create a Dask client from `config_cluster.yaml`;
- convert PHY and BGC outputs when the source contains both;
- use the configured converter for config mode;
- shut down the Dask client;
- include timestamped `__main__` logging;
- be registered in `setup.py` under `entry_points`.

## 6. Update configuration

Add `<DB>_PHY` and `<DB>_BGC` entries to
`crocolaketools/config/config.yaml` when both variants exist. Include:

- `db`;
- `db_type`;
- `input_path`;
- `outdir_pq`;
- `outdir_schema`;
- `fname_pq`;
- `add_derived_vars`;
- `overwrite`;
- `tmp_path` where needed.

Add a suitable Dask profile to
`crocolaketools/config/config_cluster.yaml`.

Use paths and names consistent with the existing demo datasets.

## 7. Check CrocoLake symlink behavior

`generate_crocolake_symlinks.sh` discovers configured `outdir_pq` entries
generically by `db_type`. A new database normally requires no script change;
adding correct PHY/BGC configuration entries is what makes it eligible for
symlink creation.

Verify that:

- the output directories exist after conversion;
- `generate_crocolake_symlinks.sh PHY` and `BGC` include the new dataset;
- existing exclusions for CrocoLake and Argo directories remain intact;
- generated links point to the expected Parquet directories.

## 8. Add tests

Add focused converter tests in `crocolaketools/test/test_converter.py` for:

- source reading and standardization;
- expected columns and dtypes;
- QC filtering;
- error-column behavior;
- profile-ID generation.

Add source-to-Parquet data-integrity tests in
`crocolaketools/test/test_data.py`, following the existing helpers. Tests
should compare representative source values with Parquet values after:

- applying the source-to-CrocoLake rename map;
- converting source missing values;
- applying source QC semantics;
- matching by platform, time, position, and pressure/depth.

For profile-based datasets, also verify:

- no duplicate rows within a profile;
- rows are sorted by increasing pressure;
- `CYCLE_NUMBER` starts at `1` for every platform in the unfiltered profile
  mapping;
- the documented composite profile key maps all observations to one profile;
- bottle/sample numbers do not create separate profiles.

## 9. Validate end to end

Run the smallest useful checks first:

```bash
python -m py_compile crocolaketools/converter/converter<DB>.py \
    scripts/<db>2parquet.py
git diff --check
```

Then run targeted tests and convert the supplied demo data. Inspect both
Parquet outputs with Dask:

```python
import dask.dataframe as dd
ddf = dd.read_parquet("<output-directory>")
ddf.head()
```

Check row counts, schemas, profile ranges, PHY/BGC variable placement,
missing-value behavior, pressure ordering, and symlink targets. Do not claim
completion based only on output directories being created.

## 10. Final review checklist

- [ ] Source documentation was inspected.
- [ ] PHY/BGC variable split is documented and mapped.
- [ ] `db_names.py` and `db_params.py` are complete.
- [ ] Profile identity and per-platform progressive numbering are correct.
- [ ] Dask operations use partition-aware functions.
- [ ] Converter script follows existing style.
- [ ] CLI entry point is registered.
- [ ] `config.yaml` and `config_cluster.yaml` are updated.
- [ ] Symlink generation includes the new outputs.
- [ ] Converter tests and source-to-Parquet integrity tests exist.
- [ ] Demo conversion and targeted validation completed.

## 11. Update this guide after approval

Once the developer has reviewed and approved the converter implementation, the
agent must update this file with durable information learned during the work.
Add concise guidance that will help future converter tasks, especially:

- dataset-specific edge cases;
- source QC or missing-value behavior that is easy to misunderstand;
- profile or cycle-number semantics;
- Dask limitations or required partition-aware patterns;
- configuration, symlink, or validation requirements;
- commands that were verified to work;
- implementation pitfalls that future agents should avoid.

Only record stable, reusable knowledge. Do not add task-specific status,
temporary paths, credentials, or assumptions that were not verified. Keep the
instructions consistent with the codebase and cite the relevant converter,
test, configuration, or documentation file when practical.
